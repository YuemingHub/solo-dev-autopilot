# 产品谱系：原始意图 → 协议实现 → MingOS 验证

## 1. 为什么需要这份谱系

知行合伙人不是从技术框架开始的，而是从一个长期使用 AI 的非技术创作者的真实困难开始的：

- 有想法，但不知道如何形成可执行需求。
- 面对大量 Agent、Skill、MCP 和工具，不知道应该选择什么。
- AI 能生成，却经常不能可靠完成。
- 长任务需要用户不断催促、解释、纠错和验收。
- 换 Agent、换会话或中断后，工作容易丢失。
- 用户不得不同时扮演产品经理、架构师、项目经理、测试人员和运维人员。

因此，产品的原始命题不是“再做一个 AI 平台”，而是：

> 让一个有专业、有判断、有想法，但不懂完整技术工程的人，也能把复杂想法可靠地推进为真实成果。

## 2. 三层正式关系

```text
原始产品意图
  用户为什么需要它、它不能变成什么
            ↓ 编译
当前协议实现
  Agent 应怎样理解、规划、执行、验证和恢复
            ↓ 应用
MingOS 真实验证
  在复杂、长期、受伦理与安全约束的项目中证明或推翻协议
            ↓ 反馈
协议候选改进
```

这不是单向交付，而是受治理的学习闭环。

## 3. 第一层：原始产品意图

### 3.1 不变命题

- 用户负责“知”：表达想法、确认方向、保留价值判断和必要的人类行动。
- Agent 负责“行”：澄清、拆解、执行、验证、记录、恢复和交付。
- 用户不需要先成为 AI 工具专家。
- 产品不是首期独立 Web 平台。
- 产品不绑定单一 Agent、模型或厂商。
- Skill 定义工作方法；MCP 和工具提供能力。
- 用户界面保持“我在 / 你先做”的自然语言。
- 少人为干预，不等于取消人的决定权。
- 交付成果本身，报告不能替代成果。
- 没有证据，不算完成。

### 3.2 不能退化成什么

- 提示词合集。
- 多 Agent 自由聊天。
- 自动化工具市场。
- 让用户填写复杂需求表。
- 以长时间运行代替有效推进。
- 以 Agent 自述代替验证。
- 以“你先做”解释为无限授权。
- 以技术实现反向改写产品原意。

## 4. 第二层：当前协议实现

当前协议将原始意图编译为七类工程：

1. Requirement Engineering：把关键方向说明白。
2. Context Engineering：给正确角色最小充分上下文。
3. Prompt Engineering：规定节点角色、输入、输出和停止条件。
4. Graph Engineering：把目标编译成有依赖的任务网络。
5. Loop Engineering：观察、计划、行动、验证、检查点。
6. Evidence Engineering：以可复查证据判断完成。
7. Authority Engineering：区分在场、委托和真实权限。

协议由四类资产组成：

- `SKILL.md`：核心行为契约。
- `protocol/`：详细规则。
- `schemas/` 与 `templates/`：状态和记录契约。
- `evals/`：符合性场景定义；实际运行结果必须另存证据。

## 5. 第三层：MingOS 真实验证

MingOS 不是演示项目，而是首个正式验证环境，因为它同时具备：

- 长期、多阶段开发。
- 多 Agent 与多分支历史。
- 真实产品代码和部署边界。
- 生命宪章和上位治理约束。
- 家庭与儿童相关隐私、安全和主体性要求。
- 需要专业主观判断，不能只靠自动测试。
- 用户本人是非技术产品负责人。

MingOS 验证的不是“Agent 能不能写代码”，而是：

- 是否能准确恢复当前事实。
- 是否能在上位约束下规划任务。
- 是否减少用户的机械式干预。
- 是否不会越权、伪造或隐藏失败。
- 是否能在中断、换会话和换 Agent 后继续。
- 是否能交付可审查、可验证、可回退的成果。

## 6. 反向校准原则

MingOS 中发现的问题只能按以下方式影响通用协议：

1. 记录观察，不立即改协议。
2. 区分项目特有问题与通用协议问题。
3. 为通用问题形成候选变更。
4. 增加能复现该问题的回归场景。
5. 在至少一个非原任务场景中验证不造成退化。
6. 更新版本和迁移说明。
7. 核心协议变更只进入 Draft，不自动合并或发布。

MingOS 的当前实现不能反向成为上位原则。
单次成功或失败不能直接成为通用规则。
