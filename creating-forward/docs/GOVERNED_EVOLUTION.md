# 受治理的协议演进

## 1. 目标

允许知行合伙人根据真实项目持续成熟，同时防止它在运行中自行漂移、扩大权限或覆盖原始产品意图。

## 2. 两条演进通道

### 快速工作通道

适用于：
- 文案澄清。
- 模板改进。
- 非规范性说明。
- Adapter 的项目事实更新。
- 新增测试夹具。
- 修复校验脚本错误。

Agent 可以在开发分支自动修改、验证并创建 Draft PR。

### 核心协议通道

适用于：
- 改变状态机。
- 改变完成定义。
- 改变授权边界。
- 改变用户与 Agent 的责任分配。
- 改变验证门禁。
- 改变跨 Agent 行为。
- 改变原始产品定位。

Agent 只能形成候选，不得自动发布。

## 3. 标准演进循环

```text
真实运行观察
→ 失败或摩擦记录
→ 归因到具体层
→ 判断项目特有 / Adapter 通用 / Core 通用
→ 形成变更候选
→ 增加复现测试
→ 实施最小补丁
→ 回归测试
→ 反例与跨场景测试
→ 独立审查
→ 人类批准
→ 版本发布
```

## 4. 归因层级

- product_intent：产品原意不清或冲突。
- requirement：需求基线错误。
- context：上下文缺失、过载或过时。
- prompt：角色指令和输出契约问题。
- graph：任务拆分、依赖或汇合问题。
- loop：重试、停止或检查点问题。
- evidence：证据不足或验证方法错误。
- authority：权限、在场和委托混淆。
- adapter：项目或平台专属边界问题。
- capability：Agent 或工具实际能力不足。
- implementation：代码缺陷，不属于协议问题。

禁止因为代码 bug 就扩大 Core 协议。
禁止把任何项目的专有术语写入通用 Core。

## 5. 证据门槛

核心候选至少需要：
- 一个真实失败记录。
- 一个稳定复现测试。
- 一个修复后通过的测试。
- 一个反例或相邻场景测试。
- 独立 Verifier 审查。
- 对原始意图和现有规则的影响分析。
- 迁移说明。

重大规则变更还需要人类批准。

## 6. 自主迭代允许范围

Agent 可以自行：
- 收集摩擦和失败。
- 形成问题归因。
- 提出最小修复。
- 修改候选分支。
- 增加测试。
- 运行验证。
- 更新 Draft 变更日志。

Agent 不可以自行：
- 合并核心协议。
- 发布正式版本。
- 删除安全和授权门禁。
- 将用户缺席视为同意。
- 因单一项目成功就推广为通用规则。
- 修改目标项目的上位原则。
