# Code Review — P0-P3 分级代码审查器

## 目标

分析 `git diff HEAD`（或指定范围）中的所有改动，输出结构化的分级审查报告。

## 审查级别定义

| 级别 | 名称 | 含义 | 必须修？ |
|------|------|------|---------|
| **P0** | 🔴 严重 | 安全漏洞、逻辑错误、数据丢失风险 | **必须修复，阻止合并** |
| **P1** | 🟠 重要 | 性能瓶颈、错误处理缺失、资源泄漏 | **强烈建议修复** |
| **P2** | 🟡 一般 | 代码质量、可读性、命名不规范 | 建议修复 |
| **P3** | 🔵 改进 | 最佳实践、未来优化、文档补充 | 可选，不阻塞 |

## 执行步骤

### Step 1: 收集改动范围

```bash
# 获取当前未提交的改动
git diff HEAD

# 如果有 staged 的改动也加上
git diff --cached HEAD

# 如果指定了范围
git diff <from>..<to>
```

如果没有任何改动，提示用户："当前没有需要审查的代码变更。"

### Step 2: 逐文件分析

对每个改动的文件，按以下维度检查：

#### 安全检查 (P0)
- [ ] 是否有硬编码的密钥/密码/Token？
- [ ] SQL 注入风险？（用户输入直接拼接到 SQL）
- [ ] XSS 风险？（用户输入未经转义直接渲染）
- [ ] 认证/授权是否正确？（是否有越权访问可能）
- [ ] 敏感数据是否被日志打印？
- [ ] 依赖是否有已知 CVE？（检查 package.json / requirements.txt 变更）

#### 逻辑正确性 (P0)
- [ ] 空值/undefined 处理是否完备？
- [ ] 异步操作是否有竞态条件？
- [ ] 边界条件是否考虑？（空数组、null、超大输入）
- [ ] 错误是否会吞掉？（空 catch 块）
- [ ] 数据类型转换是否安全？

#### 性能 (P1)
- [ ] 是否有 N+1 查询？
- [ ] 循环内是否有重复计算？
- [ ] 大数据量场景下是否会 OOM 或超时？
- [ ] 是否有不必要的重渲染？

#### 错误处理 (P1)
- [ ] 所有 async 函数是否有 try-catch？
- [ ] API 调用是否有超时和重试？
- [ ] 用户错误是否有友好的提示？
- [ ] 服务端错误是否有日志记录？

#### 代码质量 (P2)
- [ ] 函数是否过长（>50行）？
- [ ] 嵌套层级是否过深（>3层）？
- [ ] 变量/函数命名是否清晰？
- [ ] 是否有重复代码可以抽取？
- [ ] 类型注解是否完整？

#### 最佳实践 (P3)
- [ ] 是否遵循项目既有的架构模式？
- [ ] 是否有 TODO/FIXME/HACK 标记需要处理？
- [ ] 是否缺少必要的注释说明复杂逻辑？
- [ ] 测试覆盖率是否足够？

### Step 3: 输出审查报告

格式如下：

```markdown
# 📋 Code Review Report

> 审查范围：`<commit-hash>` 或 `HEAD` (未提交的改动)
> 审查时间：<timestamp>
> 改动文件数：<N>
> 改动行数：+<added> -<deleted>

## 📊 总览

| 级别 | 数量 | 说明 |
|------|------|------|
| P0 🔴 | N | 必须修复 |
| P1 🟠 | N | 强烈建议修复 |
| P2 🟡 | N | 建议修复 |
| P3 🔵 | N | 可选改进 |

## 🔴 P0 — 必须修复

### [P0-1] <简短标题>
- **文件**：`path/to/file.ts:<line>`
- **问题**：<一句话描述>
- **影响**：<如果不修会怎样>
- **建议修复**：
  ```diff
  - // 有问题的代码
  + // 修复后的代码
  ```

（重复每个 P0 问题）

## 🟠 P1 — 强烈建议修复

（同上格式）

## 🟡 P2 — 建议修复

（同上格式，可简化）

## 🔵 P3 — 可选改进

（列出即可，不需要详细 diff）

## ✅ 做得好的地方

（肯定 2-3 个点，保持正向反馈）

## 🎯 结论

**能否合并：** ✅ 可以 / ⚠️ 建议 P0/P1 修复后合并 / ❌ 不建议合并

**最重要的 3 个改进点：**
1. ...
2. ...
3. ...
```

## 使用方式

### 手动触发
在对话中说：
- "帮我 review 一下代码"
- "审查一下最近的改动"
- "/skill code-review"
- "code review main..develop"

### 自动触发（推荐）
配置在 git pre-push hook 或 commit hook 中：
```bash
# .git/hooks/pre-commit (或通过工具的 hooks 配置)
# 每次提交前自动运行轻量级审查
```

## 注意事项

1. **先理解再审查**：如果看不懂业务逻辑，先问清楚再下结论。不要因为"看不懂"就标记为 P0
2. **具体优于抽象**：每条问题都要包含具体的文件名、行号、修复建议。不要说"这里有问题"，要说"第 42 行的 SQL 拼接存在注入风险"
3. **区分偏好与问题**：P2/P3 是偏好和建议，不要用 P0 的语气表达 P3 的问题
4. **考虑上下文**：一个在大型项目中是 P1 的问题，在 MVP 中可能是 P3。根据项目阶段调整标准
5. **给出修复方案而不只是指出问题**：新手最需要的是"怎么修"，不是"哪里有问题"
